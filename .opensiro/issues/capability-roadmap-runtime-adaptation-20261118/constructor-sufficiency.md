## Track B — narrow original-native construction, not a portable wrapper
Hypothetical scenario: a dated first-party model/agent-runtime release notice says one allowed CLI runtime changes its lifecycle/hook/resume behavior. A town permitted to use two preapproved AgentPresetInfo names needs a safe optional planned transition for *future* Polecat or other selected role sessions.

- Trigger / evidence: add to one optional Deacon wisp a dated, read-only notice receipt (manual injection suffices for P0; never assume provider APIs). Compare the notice to concrete hook/resume/compaction/process fields in AgentPresetInfo, role-specific config and running-state constraints; keep source/ref for repeatability.
- Autonomous choice: Deacon's optional future-runtime evaluation formula chooses RETAIN, SINGLE_NEXT_SESSION_CANARY or ROLLBACK within the Overseer's explicit allowed-agent/role envelope. No provider addition or ultimate policy changes without owner authorization. Missing authority -> no effect.
- Native effect: record choice and authorization in existing Beads/wisp, call existing gt sling --agent only on a new eligible task/session to test a different preset. The future default role mapping can change only through existing config persistence after the trial outcome and fresh owner-control check. No live process kill, credential change or hidden fallback.
- Real feedback: wait for the actual future task's Witness/doctor/session outcome, link it to the input and canary, route result through native mail/Beads to Mayor and into subsequent Deacon decision; on failure/timeout/unknown revert to prior role config and report. A standalone future-warning dashboard without later task return does NOT qualify for C.
- Minimal new path: one optional future-runtime evaluation wisp/Deacon step + trusted notice receipt + guarded canary/return-to-role-config handshake. Reuse role registry, gt sling, existing state/mail and current patrol actors instead of creating a generic VSM supervisor or second agent-provider architecture.

## Alternatives and materiality
- A0: operator manually edits gt config agent settings / gt upgrade; valid native baseline but does not constitute autonomous outside-then organizational intelligence.
- A1: use current cost tiers or existing #2784 task router; can optimize S3 dispatch, but no independent future release interpretation and return. #1143 proposes a different longitudinal cost signal.
- A2: adding a static provider or external notice scraper alone is a useful maintenance fix but lacks whole S4 decision/effect/return; not a qualifying alternative.
- P0 selected: prototype bounded Deacon future-runtime lifecycle only. P1 authority tests, constrained one-spawn canary, evidence and rollback. P2 optional release feed; never required to claim mere architectural GO.
